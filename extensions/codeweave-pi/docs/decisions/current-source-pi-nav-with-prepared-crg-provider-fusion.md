# Current-source pi-nav with prepared CRG evidence for codeweave-pi provider fusion

## Current status

This record preserves the earlier live-binder/CRG fusion rationale; it is not current implementation authority. The selected coherent-analysis revision is in [pi-nav-owned-backend.md](pi-nav-owned-backend.md#coherent-analysis-execution-revision--approved-2026-09-08), and [the native search architecture](../../native/pi-nav/ARCHITECTURE.md#search-seed-identity-and-source-evidence) owns current source/relationship composition. CRG has since been retired from the source, so the retention argument below is closed rather than pending: keep reading it as rationale and rejected alternatives, not as an open option. Neither this historical proposal nor the isolated candidate activates a new runtime or automatic index. The sections below describe their original decision context.

## Decision

codeweave-pi implements current owner identity, TypeScript/JavaScript alias and re-export resolution, `tsconfig`/package path binding, call-site carriers, exact source ranges, and immutable query-result state in pi-nav. The live resolver uses deterministic RepoSkein-style resolution semantics but does not vendor RepoSkein crates or add a prepared alias store.

CRG was the initial prepared owner for FTS5 plus local MiniLM reciprocal-rank conceptual candidates and relationship classes that remained materially stronger after current-source rebinding. Every CRG row was a candidate until its owner and carrier were reconciled with current pi-nav identity and source proof. Slice 10 of `.pi/goals/codeweave-pi-unknown-codebase-harness/provider-fusion-implementation-plan.md` would have reassessed CRG capability by capability; retention was never permanent by default, and it is now closed.

codeweave-pi adds no RepoSkein, Semble, Pluck, or Potion runtime in the first implementation. Graphify, QMD, Git/diff, and optional LSP keep their distinct evidence roles rather than being absorbed into one code engine.

This technical selection follows the founder's authorization to implement the best evidence-selected fusion. It does not claim that the founder separately approved each provider choice.

## Context and decisive trade-off

The required result combines two properties no inspected engine supplied alone: stable owner resolution through aliases/re-exports and current edit-ready call carriers. In the P1 fixture, RepoSkein resolved 2/3 alias routes but omitted `tsconfig` paths and retained no call-site lines; CRG resolved 1/3 while retaining carrier lines; current pi-nav resolved 0/3 aliases but owned current scanning, enclosing owners, and source. P3 then proved a focused pi-nav module could resolve all three routes while preserving carrier file, line, owner range, and source, with cycle and known-module hard-stop behavior and no new dependency.

For conceptual search, P2 held one 679-owner Rust representation constant. MiniLM plus BM25F reciprocal-rank fusion led the bounded comparison; Potion and Potion v2 did not beat MiniLM on any aggregate. CRG already implements the winning mechanism class. Adding Semble, Pluck, or another model runtime would increase lifecycle and maintenance cost without a demonstrated quality gain.

The decisive criterion is current trust with the smallest coherent maintenance surface—not engine consolidation for its own sake. A focused pi-nav binder reuses the parser and carrier model already required for live search. Vendoring RepoSkein core plus language extractors would add a second fact model; a prepared resolver store would reintroduce a stale window; removing CRG before the fused live system proves equivalent conceptual and typed-relationship reach would discard verified capabilities.

## Alternatives worth remembering

- **Vendor RepoSkein core and six language extractors:** rejected for the first implementation because P3 proved the necessary TypeScript/JavaScript ladder can reuse pi-nav facts without a second parser/extractor stack. Reopen only if production coverage approaches duplicate-parser scale.
- **Run RepoSkein as another prepared provider:** rejected because alias truth must be current and RepoSkein lacks edit-ready carrier lines.
- **Embed Semble or Pluck for semantic search:** rejected by P2's lack of quality gain and by lifecycle limits. Semble rebuilds per construction and its pinned checkout lacks a license file; Pluck has unstable incremental chunk IDs and leaf-name relationship identity.
- **Remove CRG immediately:** rejected because CRG still provides the selected prepared semantic mechanism and verified typed relationships. Reduction follows measured post-fusion parity, not preference.
- **Make LSP the core resolver:** rejected because server availability varies and the parser mechanism can own normal alias resolution. LSP remains optional corroboration.

## Consequences and implementation obligations

- `native/pi-nav/src/search/bindings.rs` must stay a focused current-source module, fail closed on cycles and known-module misses, preserve deterministic carriers, and advertise language/export coverage honestly.
- Exact and exhaustive grep remains independent from conceptual ranking. Rank one never becomes ownership without the current mechanical owner gate.
- Prepared facts retain origin, generation, direction, completeness, and contradictions. Missing or stale prepared state fails open to useful live pi-nav evidence.
- The CRG lifecycle implemented at the time was no-daemon: `scripts/navigation-freshen.mjs` owned snapshot/update/validation/external-drift work, while `src/core/prepared-mutation.ts` scheduled codeweave-pi edits into that owner. Stale daemon descriptions must be removed.
- No query installs, downloads, indexes, repairs, or mutates provider state.
- RepoSkein Apache-2.0 resolution semantics and CRG path-resolution influence remain attributed in the focused implementation. Actual copied code, if any, requires matching notice and license treatment.
- The compact current call-site projection remains governed by `docs/decisions/provisional-compact-live-callsite-projection.md`.

## Revisit conditions

Revisit the focused pi-nav binder if production support requires a second extractor graph, exceeds the implementation plan's stop bound, or cannot preserve current carrier fidelity. CRG retention is closed: the code lane is the package-owned indexed Core, so that revisit condition no longer applies. Revisit the conceptual model only when a bounded comparison on the actual current representation shows a material gain without weakening exact search, privacy, credentials, or lifecycle reliability.

## History

The provider-fusion decision followed source audits of RepoSkein `93d3f1c`, Semble `8f8d963`, and Pluck `06e19ad`; P1 alias/re-export comparison; P2 semantic attribution; P3 current-source binder feasibility; independent Qwen, Muse, DeepSeek v4 Flash, and DeepSeek v4 Pro attacks; and coordinator verification. Earlier recommendations to vendor RepoSkein or add a new Rust semantic runtime were rejected after P2/P3 evidence changed the maintenance trade-off.
