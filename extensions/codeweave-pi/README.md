# codeweave-pi

![Animated codeweave-pi evidence handoff. A prepared relationship graph points to a candidate file, which is explicitly not edit authority. A live source read supplies complete displayed lines and a hash; the edit gate accepts seen current lines and refuses unsafe ones. The whole diagram remains legible when paused.](docs/images/codeweave-hero.gif)

I built codeweave-pi for the decisions between finding a plausible file and changing it. In an unfamiliar repository, the first search hit may be a caller, a test or a name that only looks relevant. Written intent may live elsewhere, and an index may lag behind the current code. The agent needs ways to test ownership, inspect the contract and return to exact source without treating those observations as interchangeable. The banner shows the boundary: an amber candidate must be checked against current bytes before it becomes mint edit authority. It is a schematic, not a captured run.

## Investigate the owner before trusting a hit

A plain text search is good when the agent knows exactly what to look for. It is less helpful when the task describes behavior without naming the component that owns it. The prepared [CodeGraph lane](native/analysis/README.md) makes code identities and typed relationships available to `explore`: the agent can search for a behavior, inspect a candidate's neighborhood, then use `trace` when one caller, import or test relationship could change its assessment. Tests and helpers can locate a subsystem without themselves proving implementation ownership. These relationships describe static evidence; a call edge does not establish what happened at runtime or every consequence of an edit. Optional Graphify maps can expose cross-domain connections when the question spans code and documentation.

Keeping preparation separate from inquiry matters here. The index has a generation and an admitted project scope. Missing or stale prepared evidence can be reported while live file search remains useful; a query does not build an index, download assets or repair the machine on the agent's behalf. That makes it possible to ask what the existing graph knows without silently changing the state being investigated. When a promising identity appears, the agent can follow its connections or return to current source. There is no required sequence of searches: the unanswered ownership question determines the next call. [The navigation doctrine](docs/harness-doctrine.md) explains this boundary in more detail.

## Ask documents what they actually say

Knowing the implementation owner does not settle the intended behavior. A current project guide might constrain a change that the code alone would permit; an old plan might describe a design that was never adopted. `docs_search` retrieves prepared QMD Markdown sections and returns a selector for reading the current section. It also shows whether retrieval was lexical or hybrid, why candidates ranked where they did, and what the page omitted. A weak lead calls for further reading, not a claim that no answer exists. pi-nav reconciles section identities against the current Markdown; a stale selector is reported as an omission. The agent can inspect the complete relevant section before deciding whether its prose governs the change.

Document metadata helps at first contact, where the agent may see a section without its context. On the first relevant `read` or `docs_search` exposure, available YAML frontmatter can show the title, description and authored `code`/`related` references with source line numbers. A per-file allowance favors those identifying rows instead of repeating a long header on every result; a changed header can appear again. If the header exceeds the allowance, the fallback shows title and description rather than silently granting authority to omitted references. Authored links still need checking against their targets; they do not prove the linked code implements the prose. This behavior applies to documents that have frontmatter; the public GitHub README has none. [The frontmatter owner](src/core/markdown-frontmatter.ts) and [QMD tests](tests/v3-qmd-docs-search.test.mjs) make that presentation choice inspectable.

## Let the question determine how much source to show

An agent investigating an unfamiliar symbol and one counting *every* use of a string are making different claims. `grep` keeps ranked discovery separate from `output:"matches"` occurrence audits. It reports the interpretation of a pattern, the searched scope, zero-result status and continuation or coverage limits. Its model-facing reply has a 4,000-reference-token ceiling; an audit that cannot fit does not quietly turn into a ranked overview. The distinction protects a negative claim from being made on a partial result. For YAML, JSON and TOML matches, syntactic key context can show where a value sits without granting edit authority over the unshown parent or siblings.

The same restraint applies to code and document retrieval. Bounded result pages leave the agent room to choose a more precise next question; visible generation, weak leads and omissions say when a page cannot close the claim. `read` can then select exact lines, a code symbol, a Markdown section or several small slices. Compactness is useful only while the route back to the current source survives it. The [tool reference](docs/tool-operating-reference.md) documents the accepted calls and the coverage each reply reports.

## Use what was seen, and no more

Once the agent has identified the right boundary, it still needs authority over the bytes it proposes to change. `read` displays numbered current lines under `[path#hash]`. A complete verbatim row already shown by `grep`, `explore` or `trace` can also receive that hash after [source authority](src/core/source-authority.ts) checks it against live pi-nav source. The agent need not reread identical certified lines solely to pass them into `edit`. A locator, clipped excerpt, transformed row or hidden proof payload cannot authorize unseen source. This separates useful context for deciding *where* to work from permission to change a particular line.

The [edit engine](src/core/patch-apply.ts) applies a small program against the hash and the line numbers the agent actually saw. It checks the file again, can carry an unchanged observed row through safe external drift, and holds changed or ambiguous targets. Its result names residual work instead of inventing missing source. Each physical file lands atomically; a later file's failure does not roll back one already changed, so the agent must read the per-file outcome. Syntax or LSP feedback and a focused test can examine the result, but a clean edit and a green check still do not prove that the original task was understood correctly. [Live-source tests](tests/v3-live-source-authority.test.mjs) cover complete-row certification and unseen-line refusal; [recovery tests](tests/v3-edit-recovery.test.mjs) exercise the ambiguous-anchor boundary.

The focused tests establish the handoff: complete displayed rows can become editable without a second read, while hidden or changed rows cannot. They do not tell us how often a model recognizes the right owner, chooses to widen a weak result or delivers a better change. Those are separate agent-behavior questions, as is whether the runtime in a fresh installation matches this source.

## Source and installation limits

This public source snapshot omits the prebuilt pi-nav executable and native module, the locally adapted vendor tree and the production Core payload with its pinned code model. **A bare clone cannot install the complete codeweave-pi runtime.** A future publisher-prepared checkout needs Pi, Node.js 22.19 or newer, npm, Git and matching Core/native/model assets. That declared Node floor does not prove ABI compatibility for every native build. The `npm run install:codeweave-pi` flow checks prepared assets, provisions and exercises roughly 928 MiB of QMD models with first-install network and disk cost, and registers only after success. Startup does not compile or download them. Python 3.10–3.14 with `venv` is needed only for optional Graphify. Do not register codeweave-pi alongside a second copy or the jeito aggregate.

[Setup](docs/setup.md) owns the development and recovery path; [current truth](docs/current-truth.md) separates source tests and isolated candidates from loaded Pi and clean-package evidence. [Grep coverage tests](tests/v3-grep-cap-fallback.test.mjs), the [evidence map](docs/evidence.md) and the [mutation decision record](docs/decisions/proof-preserving-mutation.md) show the narrower proof and its limits. The root [installation guide](../../docs/getting-started.md), [distribution gaps](../../docs/publication-readiness.md) and [third-party notices](THIRD_PARTY_NOTICES.md) complete the picture before a supported release.
